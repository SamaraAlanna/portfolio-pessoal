::::secao{rotulo="Leads" titulo="Leads chegando sem CPF válido"}
Recebi uma demanda para investigar o motivo dos leads estarem chegando sem um CPF válido. Após uma análise identifiquei que o HTML só conferia o tamanho, a máscara formatava sem validar, o servidor confiava só no front e o endpoint aceitava envio de bot. Para solucionar escrevi um módulo PHP, um JavaScript compartilhado, e um deploy alcançou as 77 páginas.

:::codigo{arquivo="validacao.php" abas="Antes, Depois" prova="true"}
```html
<input name="cpf" pattern=".{11,14}" required>

$("#cpf").mask("000.000.000-00")
if (cpf.length >= 11) enviarLead(form)

// no servidor: nenhuma verificação
```

```php
function cpf_valido(string $cpf): bool {
  $cpf = preg_replace("/\D/", "", $cpf);
  if (strlen($cpf) !== 11) return false;
  if (preg_match("/^(\d)\1{10}$/", $cpf)) return false;
  return digitos_verificadores_ok($cpf);
}
```

::::secao{rotulo="Versionamento" titulo="De FTP ao deploy automático"}
O método utilizado era o FTP Manual, e ele trazia muitos problemas ao dia a dia da equipe e demandava muita comunicação, pois sem o versionamento git, os arquivos eram sobrescritos todos os dias, então como iniciativa pessoal, decidi adicionar o controle de versão git, com a criação do repositório no GitHub.

::::secao{rotulo="Performance" titulo="Um cache desligado por uma linha"}
Um `session_start()` no cabeçalho, carregado por cerca de 150 templates, fazia o PHP desligar o cache de todas as páginas. Centralizei a sessão num hook que só abre quando há formulário, e estendi o cache às visitas de campanha, que chegavam com parâmetros de UTM e passavam direto.

:::
